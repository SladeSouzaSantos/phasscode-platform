# HydraDB official documentation v2 vs our v0.3.0 Orbe experiment

**Prepared:** 2026-11-06. **Purpose:** pre-send technical review of the questions to Nishkarsh; factual documentation comparison, **not** v2 runtime acceptance. **Scope:** only branch \`experiment/hydradb\`, no calls to authenticated HydraDB Cloud, no DEV/MAIN/MiniMac changes.

## Critical version/product boundary

Our existing Gates 9–16 ran **self-hosted open-source HydraDB v0.3.0** from a pinned GHCR container, using **\`POST /v1/graphs/lab/query\`**, Neo4j-driver-compatible Bolt and explicit S3-compatible MinIO in the isolated lab. We did **not** test the managed **HydraDB Cloud API v2**, its hosted **\`POST /byog/query\`**, the managed v2 retrieval pipeline, or **\`@hydradb/sdk\`**. **The hosted API's feature descriptions are not proof that the v0.3.0 local engine implements those features in the same way.** In particular, \`API-Version: 2\` is an HTTP API version and **not** the open-source graph engine's release number. Distinct endpoints, response envelopes, SDK semantics, storage services and potential licensing must not be conflated.

Primary official sources, accessed 2026-11-06:

- [v2 Introduction](https://docs.hydradb.com/get-started/v2/introduction): managed unified AI context layer, memory/knowledge/graph, serverless API.
- [v2 API Reference](https://docs.hydradb.com/api-reference/v2): HTTP \`/databases\`, \`/context/ingest\`, \`/context/status\`, \`/query\`; auth \`Bearer\` plus \`API-Version: 2\` for the standard API.
- [v2 SDKs](https://docs.hydradb.com/api-reference/v2/sdks): official \`@hydradb/sdk\` 2.1.x for TypeScript and Python \`hydradb-sdk\`; \`HydraDBClient.query\` is **retrieval**, not a drop-in Neo4j Bolt/Cypher driver.
- [v2 Bring Your Own Graph (BYOG)](https://docs.hydradb.com/essentials/v2/bring-your-own-graph): separate **hosted** \`POST /byog/databases\`, \`POST /byog/query\`, graph collections, Cypher examples, \`params\`, migration from Neo4j, row format, error handling, indices, upserts.
- [v2 Query Overview](https://docs.hydradb.com/api-reference/v2/endpoint/query-overview): hybrid/text retrieval; \`fast\`/\`thinking\`/\`auto\`; \`graph_context\`, metadata filters, collections, source chunks. This is not a raw Cypher query endpoint.
- [v2 Context Relations](https://docs.hydradb.com/api-reference/v2/endpoint/source-relations), [v2 Connected Subgraph](https://docs.hydradb.com/api-reference/v2/endpoint/subgraph): knowledge-context provenance and neighboring sources; these are not automatically equivalent to the Orbe claim/source repository contract.
- [v2 AI LinkedIn Recruiter cookbook](https://docs.hydradb.com/cookbooks/v2/ai-linkedin-recruiter): a recruiting-app example using candidate metadata, natural language and retrieval; analogous use case but **not Orbe-specific validation**.
- [HydraDB hosted pricing](https://hydradb.com/pricing): publishes the **current listed hosted plan and storage rates**, not observed self-hosted total-cost-of-ownership or S3 traffic in our experiments.
- [Open-source repository README](https://github.com/hydra-db/hydradb/blob/v0.3.0/README.md), [original changelog](https://github.com/hydra-db/hydradb/blob/v0.3.0/CHANGELOG.md), [openCypher subset](https://github.com/hydra-db/hydradb/blob/v0.3.0/docs/openCypher.md): different release-specific authoritative sources for self-hosted v0.3.0. Confirm exact paths from upstream before quoting detailed support; our CI logs are the primary evidence of behavior.

## Additional relevant information for the Orbe architecture

1. **v2 Cloud managed retrieval**: \`POST /query\` returns ranked source chunks, stable source metadata, optional graph context and a formatted \`llm_prompt\`. This suggests a *different* option for future research: integrate Orbe as a **retrieval consumer of managed v2**, but it would change deployment, product architecture and data handling. It is **not equivalent** to testing the existing local open-source graph backend and is **not authorized** here.
2. **v2 BYOG raw Cypher**: \`POST /byog/query\` accepts \`database\`, \`collection\`, \`query\` and \`params\` and emits \`data\` as an array of aliased row objects. Our v0.3.0 lab uses a different endpoint and typed \`columns\` + \`rows\`. Their adapters **cannot be assumed wire compatible**. The v2 docs recommend externally owned keys, while the lab used numeric **physical graph IDs** with external source-key properties. Both principles can coexist.
3. **v2 graph payload ingestion**: \`graph_payload\` attaches source-specific graph entities/relations and persists across re-ingest, but the documentation states **whole-graph replacement**, limits of 5,000 entities/10,000 relationships/500 per entity, and best-matching chunk linkage. These constraints differ from Orbe's exact claim/source provenance and require separate acceptance tests.
4. **v2 SDK not equal to Bolt**: installing \`@hydradb/sdk@^2.1.7\` does **not** make \`neo4j-driver\` 6.2.0 work with HydraDB Bolt or provide the \`GraphRAG\` Orbe runtime semantics automatically. It is a possible separate, hosted API integration track, not a correction applied to the local PoC.
5. **Pricing**: listed plans such as Cloud Ship ($25/month minimum, storage $0.50/GB-month at review) and Scale ($300/month minimum, storage $0.25/GB-month) are public **vendor pricing**, not benchmark results or a confirmed invoice/quote. Prices can change. Self-hosted open-source infrastructure may still incur compute, object-store request/storage, network and maintenance costs.

## How this changes our feedback

The email should say we **consulted the hosted v2 BYOG/SDK and migration guidance and found useful answers** on Cypher over HTTPS, external business IDs, idempotent batch imports, collection isolation and source context. It should **not** ask generally how to migrate Neo4j or use the new TypeScript SDK to fix Bolt.

The unresolved high-value maintainer questions are:

1. For **self-hosted open-source v0.3.0**, what explains/works around the **JS Neo4j driver 6.2.0 versus Python driver 6.4.1** Bolt difference? How are \`lab\`, \`default\`, no database and routed URIs mapped, and what is the recommended **production-supported** JS config?
2. Are **the hosted v2 BYOG Cypher semantics and migration guidance** implemented in the same open-source engine release we tested, or are there release/transport/feature differences? Is there a recommended v0.3.0-compatible path for Orbe, or an expected newer self-hosted version?
3. Which **v0.3.0 S3/MinIO fault, crash and bookmark** tests are most relevant for an evidence-driven GraphRAG backend, beyond the successful clean-restart tests? Could the smoke script use maintained, pullable images?
4. Optional: what self-hosted **S3 GET/PUT/bytes, CPU-seconds, working set and costs** would the team track for a fair benchmark of equivalent claim/source retrieval? We have preliminary latency only.

**No additional v2 tests were performed.** This is a documentation audit and a rewrite of the questions, not a product-support or regression verdict.
